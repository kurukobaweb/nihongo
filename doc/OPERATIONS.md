## 本文書の位置づけ

本文書は、MVP テスト環境の検証に必要な最小限の運用手順を整理する。
フェーズ②（本番環境構築）以降で、監視基盤・通知チャネル・Runbook 等を段階的に拡充する。

MVP では以下を前提とする。

- Laravel 標準機能、Queue Worker、Scheduler、OS 標準機能を運用基盤とする
- 外部監視基盤（Sentry 等）、外部ログ基盤は MVP スコープ外
- 運用担当者がサーバーに SSH でアクセスできる前提
- 運用上の点検・一次対応は、MVP テスト環境で検証可能な最小範囲に限定する

設計判断の正本は `ARCHITECTURE.md`、DB 設計の正本は `DB_SCHEMA.md`、UI/UX 設計の正本は `DESIGN.md`、未確定事項の唯一の管理台帳は `OPEN_ISSUES.md` を参照する。

Feature Flag の設計、Stripe Webhook 対象イベント、管理画面 MVP 範囲など、運用に影響するが設計判断または未確定事項に属するものは、本文書へ詳細を重複させず、各正本または `OPEN_ISSUES.md` の ID 参照で管理する。

## 1. 点検対象の概要

運用上の点検対象は、稼働確認・障害調査・監査追跡・削除完了確認に必要な範囲とする。

### 1.1 主な点検対象

| 対象 | 確認場所 | 確認観点 |
|---|---|---|
| アプリケーションログ | `storage/logs/` | エラー・警告の有無 |
| Queue 滞留 | `jobs` テーブル | 処理待ちジョブの蓄積有無 |
| 失敗ジョブ | `failed_jobs` テーブル | 継続的な失敗の有無 |
| Stripe Webhook | アプリケーションログ | 処理成功/失敗の追跡 |
| 音声一時ファイル | `storage/app/audio/` | 残存ファイルの蓄積有無 |
| ヘルスチェック | `GET /health`（FastAPI） | Python サービスの生存確認 |
| ストレージ残容量 | OS コマンド（`df`） | 逼迫兆候の有無 |
| Feature Flag 反映後表示 | 結果画面 | 発音・流暢さセクションの表示/非表示が `DESIGN.md` と整合しているか |
| 管理画面 | admin ロールでのアクセス | MVP 範囲内の画面到達・基本表示の確認。具体範囲は OI-028 で管理 |

Stripe Webhook の対象イベント一覧は OI-027 で管理する。本文書では、Webhook 処理の成功/失敗、継続失敗、契約状態同期への影響確認を運用点検対象とする。

STT 認識不可時の 422 は、原則として通常のシステム障害ではなく、ユーザー再提出 UX の対象として扱う。ただし、422 が短時間に急増する場合は、録音品質・ブラウザ録音・音声形式変換・Azure STT 応答傾向の調査対象とする。

### 1.2 処理経路ごとの追跡

単なる稼働有無ではなく、以下の各経路が正常終了・失敗・再試行のいずれの状態かを追跡可能であることを重視する。

- 提出受付 → 音声評価 → 結果保存 → 音声削除
- Stripe Webhook 受信 → 契約状態更新
- 退会: Stripe 解約 → 音声削除 → soft delete → 30日後 hard delete

音声提出経路では、422 音声認識不可を 500 / 502 / 503 / タイムアウトと同列のサーバー障害として扱わない。422 は、原則として提出フロー内でエラー表示後に再録音 / 再提出へ戻す対象とする。

管理画面の運用点検は、単一 `admin` ロールでのアクセスを前提とする。MVP で運用前提にする管理画面の最小範囲は OI-028 確定後に具体化する。

## 2. 定期運用

MVP では Laravel Scheduler を定期運用の起点とする。

### 2.1 定期確認項目

| 確認項目 | 頻度（目安） | 方法 |
|---|---|---|
| 残存一時音声ファイル | 日次 | `storage/app/audio/` 内の古いファイル有無 |
| `failed_jobs` 滞留 | 日次 | テーブル件数確認 |
| Stripe Webhook 失敗 | 日次 | ログ確認 |
| バックアップ成否 | 日次 | バックアップジョブの結果確認 |
| ストレージ残容量 | 週次 | `df -h` 相当 |
| 422 急増傾向 | 必要時 | アプリケーションログ、音声評価ログの傾向確認 |

422 急増傾向の確認は、通常障害の断定ではなく、録音品質・ブラウザ録音・音声形式変換・Azure STT 応答傾向の品質調査として扱う。

### 2.2 定期ジョブ（MVP 想定）

| ジョブ | 概要 | スケジュール |
|---|---|---|
| CleanupTempFilesJob | 即時削除に失敗した音声一時ファイルを回復的に削除 | OI-021 で管理 |
| （将来）HardDeleteExpiredUsersJob | soft delete から30日経過したユーザーの hard delete | 実行主体は OI-105 で管理 |

Scheduler の具体的なジョブ一覧の最終構成は OI-001 で管理。
クリーンアップバッチの実行頻度および削除対象条件は OI-021 で管理。
hard delete 実行主体の確定は OI-105 で管理。

CleanupTempFilesJob は、音声一時ファイルの即時削除失敗時の回復手段である。音声ファイルを永続保存するための仕組みではない。
音声一時ファイルはバックアップ対象外であり、削除失敗時はバックアップから復元するのではなく、残存ファイルの削除により整合性を回復する。

## 3. 障害検知と一次対応

### 3.1 検知対象

| 検知対象 | 兆候 |
|---|---|
| アプリケーション稼働異常 | HTTP 応答なし、5xx 頻発 |
| Queue Worker 停止 | `jobs` テーブルにジョブが蓄積し処理されない |
| `failed_jobs` 継続滞留 | 件数が日次で増加し続ける |
| Stripe Webhook 継続失敗 | Webhook ログに連続失敗記録 |
| 音声削除失敗の継続発生 | `storage/app/audio/` にファイルが蓄積 |
| DB 接続異常 | アプリケーションログに接続エラー |
| ストレージ逼迫 | 残容量がしきい値以下 |
| FastAPI 接続タイムアウト | `/health` 応答なし |
| 422 音声認識不可の急増 | 通常より高い頻度で音声認識不可が発生 |

422 音声認識不可は、原則として運用障害ではなくユーザー再提出 UX の対象である。
ただし、急増時は録音品質・ブラウザ録音・音声形式変換・Azure STT 応答傾向の品質調査対象とする。

### 3.2 一次対応の基本順序

1. 影響範囲の確認（どの処理経路が影響を受けているか）
2. 再試行連鎖の抑制（必要に応じて Queue Worker 一時停止）
3. ログと失敗情報の保全
4. 安全な単位での再実行またはプロセス再起動
5. DB・課金・削除状態の整合確認

500 / 502 / 503 / タイムアウトはリトライ・障害調査対象とする。
422 音声認識不可はリトライ前提のサーバー障害ではなく、UI 上でエラー表示後に再録音 / 再提出へ戻す対象とする。

### 3.3 FastAPI 接続タイムアウト時

Laravel から Python サービスへの接続タイムアウト発生時は、1回目の再試行前に `/health` を確認する。
応答がなければジョブを即 failed として扱い、障害ログを出力する。
（ARCHITECTURE.md §4.3 のタイムアウト設計と整合）

500 / 502 / 503 / 接続タイムアウトはリトライ対象とする。
422 音声認識不可は原則としてリトライ対象外とし、提出フロー上の再録音 / 再提出へ戻す。

### 3.4 Stripe 連携異常

Webhook の一時失敗と継続失敗を区別する。
継続失敗時は契約状態・課金状態・アプリ側状態の整合に影響しうるため、優先確認対象とする。

確認観点は以下とする。

- Webhook 受信ログが記録されているか
- 署名検証エラーが継続していないか
- Webhook 処理ジョブが Queue に滞留していないか
- `failed_jobs` に Webhook 関連ジョブが継続して記録されていないか
- Stripe 側の契約状態とアプリ側の契約状態に不整合がないか

MVP で処理対象とする Stripe Webhook イベントの最小範囲は OI-027 で管理する。
OI-027 確定前に、本文書でイベント一覧を確定済みとして扱わない。

### 3.5 STT 認識不可時（422）

422 音声認識不可は、無音・ノイズ・録音品質・音声形式等により STT が評価可能な入力を得られなかった状態として扱う。
通常の 500 / 502 / 503 / タイムアウトとは区別する。

運用上の扱いは以下とする。

- 原則として運用障害ではなく、ユーザー再提出 UX の対象とする
- UI 上はエラー表示後に再録音 / 再提出へ戻す
- 空欄の結果画面へ進めない
- 発音・流暢さ・速度等の未評価項目を空欄や NULL としてユーザーに表示しない
- 詳細なユーザー向け説明文言、再録音導線、エラー表示方針は OI-006 で管理する

ただし、422 が急増する場合は以下を調査する。

- 録音品質
- ブラウザ録音
- 音声形式変換
- Azure STT 応答傾向

### 3.6 音声削除失敗

音声削除失敗が発生した場合でも、評価結果保存済みであれば DB メタデータの整合を優先する。
そのうえで、残存一時ファイルは CleanupTempFilesJob により回復的に削除する。

確認観点は以下とする。

- `storage/app/audio/` に古いファイルが蓄積していないか
- 削除失敗ログが継続発生していないか
- 対象 submission の状態が `completed` または `failed` に確定しているか
- 退会フロー中の音声再走査・削除が失敗していないか

CleanupTempFilesJob の実行頻度および削除対象条件は OI-021 で管理する。

### 3.7 通知方針

通知チャネルの最終決定は OI-019 で管理。
MVP では「検知できること」を優先し、通知手段の高度化は後続で判断する。

## 4. リリース・変更反映

### 4.1 基本原則

- 本番以外の環境で確認を経てから本番反映する
- アプリケーション変更、設定値変更、DB スキーマ変更、Feature Flag 変更のいずれにも適用
- デプロイと機能有効化を分けて扱える状態を維持する
- 未確定事項に属する変更は、該当 OI の確定後に運用手順へ反映する

### 4.2 リリース単位

以下を単一リリース単位として扱う。

- アプリケーションコード
- DB マイグレーション
- 設定変更（Feature Flag / `.env`）
- フロントエンドビルド成果物

### 4.3 変更反映前の確認項目

| 確認項目 | 備考 |
|---|---|
| アプリケーション基本疎通 | — |
| Queue Worker 稼働 | — |
| 音声提出 → 結果保存の基本経路 | E2E 確認 |
| 一時音声削除の基本動作 | 音声ファイル非永続保存方針と整合確認 |
| Stripe Webhook 受信経路への影響 | 対象イベント一覧は OI-027 確定後に反映 |
| 退会フロー4段階への影響 | Stripe 解約 → 音声削除 → soft delete → 30日後 hard delete |
| 管理画面への影響 | admin ロール前提。MVP 範囲は OI-028 に従う |

### 4.4 マイグレーション方針

- 本番反映時は明示的にマイグレーションを実行する
- 破壊的変更は段階的マイグレーションで回避する
- DB は安易な `rollback` 前提にせず、前方修正を基本とする
- DB 詳細は `DB_SCHEMA.md` を正本とし、本文書には重複記述しない

### 4.5 Feature Flag 反映

Feature Flag の設計正本は `ARCHITECTURE.md §6` とする。
本文書では反映手順と確認観点のみを扱う。

リリース時は以下を基本とする。

1. `.env` を更新する
2. Laravel の設定キャッシュをクリアまたは再生成する
3. Queue Worker / アプリケーションプロセスが新しい設定を参照していることを確認する
4. 結果画面で Feature Flag に応じた表示/非表示を確認する

デプロイと機能有効化を分けて扱えることを前提とする。

Feature Flag OFF 時は、結果画面で発音・流暢さセクション自体を非表示にする。
空欄・NULL・未評価などの内部状態をユーザーに表示しない。
Feature Flag ON 時は、PoC 結果および OI-012 の判断に基づき、表示内容が `DESIGN.md` と整合していることを確認する。

Feature Flag のキー、管理方式、Python 側への伝達方式は `ARCHITECTURE.md §6` を参照し、本文書では設計正本を重複管理しない。

### 4.6 ロールバック方針

- アプリケーションコードは直前安定版へ戻せるようにする
- 失敗時の対応順: アプリ停止判断 → 影響範囲確認 → 前方修正 or 安定版復旧
- DB 変更は安易な rollback 前提にせず、前方修正を基本とする
- Feature Flag 由来の不具合は、可能であれば機能 OFF に戻して影響を限定する

### 4.7 ブランチ戦略

Git ブランチ戦略の最終確定は OI-018 で管理。
CodeX 作業ブランチ、開発統合ブランチ、本番反映ブランチの扱いは OI-018 確定後に運用へ反映する。

OI-018 確定前は、本文書でブランチ戦略を固定しない。
少なくとも本番反映対象ブランチを1本定めることを前提とし、実装開始前に作業ブランチ・統合先・main 反映フローを明確にする。

## 5. バックアップ・復旧

### 5.1 バックアップ対象

| 区分 | 対象 |
|---|---|
| 対象 | PostgreSQL 業務データ、Laravel 設定のうち永続化が必要なもの |
| 対象外 | 一時音声ファイル、再生成可能キャッシュ、ビルド成果物 |

音声一時ファイルはバックアップ対象外とする。
音声ファイルは永続保存しないため、障害時の復旧対象に含めない。

### 5.2 運用上の確認項目

- バックアップジョブの成否
- 対象範囲の妥当性
- 復旧に必要な世代が保持されているか
- 復元手順が成立するか（取得成功でも復元不可なら不十分）
- DB メタデータ、課金整合、退会状態整合の回復に必要な情報が保持されているか

### 5.3 障害時の復旧順序

1. 障害範囲の確認
2. 復旧対象と復旧時点の選定
3. 安全な場所での復元確認
4. 本番復旧の実施判断
5. アプリケーション整合確認
6. Stripe / 同意履歴 / サブスクリプション整合確認
7. 退会状態・soft delete / hard delete 対象の整合確認

音声ファイルは復旧対象に含めない。
DB メタデータ・課金整合・退会状態整合の回復を優先する。
残存音声ファイルがある場合は、バックアップから復元するのではなく、削除状態の再確認と CleanupTempFilesJob による回復を行う。

### 5.4 外部保管先

外部バックアップ保管先、暗号化方式、復旧責任者は OI-020 で管理。

## 6. Secrets・API キー・設定値

### 6.1 基本原則

- 環境分離: 本番の Secrets を本番以外で流用しない
- 最小権限: 用途ごとに認証情報を分離する
- 変更追跡: 変更時に影響範囲を確認できること
- 設定変更後は、影響する処理経路の疎通確認を行う

### 6.2 管理対象

| 対象 | 備考 |
|---|---|
| Stripe 連携情報 | API キー、Webhook シークレット |
| Azure AI Speech 連携情報 | API キー（Key1 / Key2） |
| 内部通信トークン | X-Internal-Token（Laravel ⇔ Python） |
| DB 接続情報 | — |
| APP_KEY | Laravel アプリケーションキー |
| Google OAuth 認証情報 | Client ID / Secret |
| Feature Flag 設定値 | `.env` 変更時は `config:cache` クリアと動作確認が必要 |

Feature Flag に関する `.env` 変更後の反映手順は §4.5 と整合させる。
Feature Flag の設計詳細は `ARCHITECTURE.md §6` を参照する。

### 6.3 ローテーション

- Azure API キーは Key1 / Key2 の切替で無停止ローテーション可能
- 内部通信トークンのローテーション方針は OI-007 で管理
- Azure API キーローテーション手順は OI-013 で管理

### 6.4 設定変更後の確認

設定変更時は、変更後の疎通確認を必須とする。
特に以下の経路は認証情報・設定値変更の影響を受けやすいため、確認対象から外さない。

- 音声評価経路
- Stripe 連携経路
- Queue 処理経路
- Feature Flag による結果画面の表示/非表示
- Google OAuth 認証経路

Feature Flag に関係する設定変更では、発音・流暢さセクションの表示/非表示が `DESIGN.md` と整合しているか確認する。

## 7. 監視対象（MVP 最小構成）

MVP では外部監視ツールを前提とせず、以下の観点で「検知できること」を優先する。

### 7.1 ヘルスチェック

| エンドポイント | 提供元 | 確認内容 |
|---|---|---|
| Web アプリ基本疎通 | Laravel | HTTP 200 応答 |
| `GET /health` | FastAPI | Python プロセス生存 + Azure 接続状態 |

### 7.2 ログベースの異常検知

| 対象 | 異常兆候 | 確認方法 |
|---|---|---|
| `failed_jobs` | 件数急増 | DB クエリ / ログ確認 |
| Stripe Webhook | 継続失敗 | アプリケーションログ |
| Azure API | エラー率上昇 | アプリケーションログ |
| 音声削除 | 継続的な削除失敗 | アプリケーションログ |
| 422 音声認識不可 | 通常より高い頻度で発生 | 傾向調査 / 品質調査 |

422 音声認識不可の増加は、通常障害として即断せず、傾向調査または品質調査として扱う。
調査観点は、録音品質・ブラウザ録音・音声形式変換・Azure STT 応答傾向とする。

Stripe Webhook については、処理成功/失敗の追跡、一時失敗と継続失敗の区別、契約状態更新・課金状態・アプリ側状態の整合確認を監視観点として維持する。
Webhook 対象イベント一覧は OI-027 確定後に運用点検項目へ反映する。

### 7.3 将来の拡張

外部監視ツール（Sentry 等）の導入はフェーズ②以降で検討する。
具体的な異常判定閾値は、フェーズ②以降または運用準備時に確定する。
